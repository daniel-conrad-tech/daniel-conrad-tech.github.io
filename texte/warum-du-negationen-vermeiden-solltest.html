Warum du Negationen vermeiden solltest

Eine Bedingung sollte ihre Bedeutung direkt aussprechen. Wie isEmpty() implizite String-Logik ersetzt, wann ausgeschriebene Negationen helfen und wo diese Regel ihre Grenzen hat.

Eine Bedingung sollte sagen, welchen Zustand sie prüft. Wenn ich dafür erst einen String als Wahrheitswert lesen und das Ergebnis umkehren muss, kann ein passender Methodenname die Absicht klarer ausdrücken.

Im Beitrag Sonderfälle früh abschließen habe ich den leeren Originaltext mit einer Guard Clause behandelt. Der Ablauf wurde dadurch einfacher. An der Bedingung lässt sich weiterarbeiten.

Diagnose

Der Renderer hängt den Originaltext als Zitat an eine Antwort an. Bei leerem Originaltext genügt die Antwort. Der Anfang der Methode sieht bisher so aus:

render(response: ReplyBody, original: OriginalBody): DraftBody {
    const responseText = response.toString();
    const originalText = original.toString();

    if (!originalText) {
        return DraftBody.create(responseText);
    }

Wer TypeScript kennt, kann das lesen. Trotzdem steht die Regel „Der Originaltext ist leer“ nur indirekt dort. ! wertet den String als Boolean aus und negiert ihn. Der Ausdruck !originalText ergibt bei einer leeren Zeichenkette true, bei jeder nicht leeren Zeichenkette false.

Ich würde die Bedeutung direkt benennen:

if (original.isEmpty()) {
    return DraftBody.create(responseText);
}

Muster

Ein Objekt hat bereits einen Namen aus dem Anwendungsfall: OriginalBody. Für die Entscheidung wird es trotzdem zuerst in seine technische Darstellung umgewandelt. Der Aufrufer leitet aus dieser Darstellung selbst ab, ob der Inhalt leer ist.

Damit kennt der Aufrufer zwei Dinge: wie das Objekt seinen Text liefert und wie daraus Leerheit bestimmt wird. Eine Methode isEmpty() gibt dieser zweiten Frage einen eigenen Vertrag.

Gerade beim Lesen eines Diffs oder eines einzelnen Ausschnitts kann Kontext fehlen. Ein guter Methodenname liefert einen Teil davon direkt mit.

Mechanik

OriginalBody bekommt eine Zustandsprüfung. Wenn das Objekt seinen Inhalt intern als String text hält, kann sie so aussehen:

isEmpty(): boolean {
    return this.text.length === 0;
}

Dabei muss text genau dem bisherigen Ergebnis von toString() entsprechen. Ein Text aus Leerzeichen bleibt Inhalt. Ein zusätzliches trim() würde das Verhalten ändern.

Der Renderer kann anschließend den leeren Fall behandeln, bevor er den Text zum Zitieren abfragt:

export class ReplyDraftBodyRenderer {
    render(response: ReplyBody, original: OriginalBody): DraftBody {
        const responseText = response.toString();

        if (original.isEmpty()) {
            return DraftBody.create(responseText);
        }

        const originalText = original.toString();
        const quote = originalText
            .split("\n")
            .map(line => `> ${line}`)
            .join("\n");

        return DraftBody.create(`${responseText}\n\n${quote}`);
    }
}

Diese Fassung setzt eine reine, stabile String-Darstellung voraus. Im leeren Fall wird original.toString() jetzt nicht mehr aufgerufen. Hätte dieser Aufruf Seiteneffekte, müsste der Umbau sie gesondert berücksichtigen.

Auch Symbole gehören zur Lesbarkeit

Eine zweite Frage betrifft die Schreibweise einer Negation:

if (!isAuthorized()) {
    return;
}

Ich finde die ausgeschriebene Bedingung hier klarer:

if (isNotAuthorized()) {
    return;
}

Die Negation bleibt sprachlich erhalten. Ihr Bezug steht nun im selben Namen. Das ist ein Entwurfsurteil zur Lesbarkeit, kein durch die folgenden Studien belegter Geschwindigkeitsvorteil dieses konkreten Aufrufs.

Für diesen Austausch muss isNotAuthorized() bei gleicher Eingabe exakt das negierte Ergebnis von isAuthorized() liefern. Ein eigener Zustand wie „ausdrücklich abgelehnt“ wäre ein anderer Vertrag, falls beispielsweise auch „noch ungeprüft“ vorkommen kann.

isEmpty() geht einen Schritt weiter: Es benennt den gesuchten Zustand mit einem eigenen Begriff. Bei einer Berechtigung kann die verneinte Form dagegen genau dem Fall entsprechen, den die Guard Clause abschließen soll.

Meine Entwurfsbegründung bleibt überprüfbar: Ein benanntes Prädikat macht die Absicht am Aufruf sichtbar. Ob ein bestimmtes Modell damit zuverlässiger arbeitet, müsste ein Vergleich am konkreten Code zeigen.

Gegenargument

!isAuthorized() ist für viele Entwickler vertraut und unmittelbar verständlich. Für jeden solchen Ausdruck eine Gegenmethode einzuführen, vergrößert die Schnittstelle. Wird isNotAuthorized() später selbst negiert, entsteht mit !isNotAuthorized() eine doppelte Verneinung. Eine ausgeschriebene Form ist deshalb keine automatische Verbesserung.

Auch isEmpty() hilft nur, wenn seine Bedeutung klar ist. Zählt ein Text aus Leerzeichen als leer? Gibt es unsichtbares Markup? Der Name stellt die richtige Frage; der Vertrag muss sie beantworten.

Die Empfehlung gilt dort, wo eine benannte Prüfung Bedeutung erschließt oder eine wiederkehrende Regel bündelt. Eine kurze, vertraute Negation darf bleiben, wenn eine zusätzliche Methode keinen erkennbaren Gewinn bringt. Der Titel zielt auf vermeidbare Übersetzungsarbeit beim Lesen.

Handlungsvorschlag

Lies eine Bedingung als Satz über den Anwendungsfall. Prüft sie „Originaltext ist leer“, sollte ein vorhandenes OriginalBody diese Frage beantworten können.

Prüfe bei negierten Prädikaten zusätzlich, welche Form den behandelten Fall am klarsten benennt. Berücksichtige die bestehenden Aufrufe und Begriffe. Eine neue Methode sollte eine verständliche Frage ausdrücken und einen eindeutigen Vertrag haben.

Bewahre beim Umbau die bisherige Bedeutung. Für diesen Renderer heißt das insbesondere: Nur der String ohne Zeichen ist leer; Leerzeichen bleiben erhalten.

Agentenregel

## Bedingungen direkt benennen

Wenn eine Bedingung einen Zustand aus einer technischen Darstellung
ableitet, prüfe, ob das zuständige Objekt ein passendes Prädikat
anbieten sollte, etwa original.isEmpty() statt !originalText.

Prüfe bei negierten Prädikaten, ob eine ausgeschriebene Bedingung
den behandelten Fall klarer ausdrückt. Berücksichtige vorhandene
Begriffe und Aufrufe; vermeide doppelte Negationen.

Führe zusätzliche Methoden ein, wenn sie Bedeutung erschließen
oder eine Regel bündeln. Vertraute, klar lesbare Negationen dürfen
bleiben. Begründe den Nutzen am konkreten Code.

Bewahre die Definition des Zustands, relevante Seiteneffekte und
Auswertungsreihenfolgen. Verändere insbesondere die Behandlung
von Leerzeichen nicht nebenbei.

Prüffrage

Kann ich am Aufruf sagen, welcher Zustand geprüft wird, und ist klar, welche Werte ihn erfüllen?

Im Renderer lautet die Antwort: original.isEmpty() prüft, ob der Originaltext kein einziges Zeichen enthält.

Signal

Ein gutes Zeichen: Im Review wird die Bedingung mit denselben Begriffen erklärt wie die fachliche Regel. Die Definition von „leer“ liegt in OriginalBody; Aufrufer müssen sie nicht erneut aus dem String ableiten.

Ein Warnzeichen: Es entstehen Methodenpaare ohne klaren Bedarf, Aufrufer negieren bereits negative Namen oder niemand kann erklären, ob Leerzeichen als Inhalt zählen. Dann hat die Umbenennung die Bedeutung noch nicht ausreichend geklärt.
